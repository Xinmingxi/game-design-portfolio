**性质**：竞品系统拆解 + 改进提案 ｜ **全部数值与机制为游戏内逐项实测**（采集期 2026.08–09）

| 指标 | 数量 |
| --- | --- |
| 分析文档 | 19 张表 + 7 张图 / 3 万余字 |
| 配套原始数据 | 6 份数据文件 / 56 张工作表 |
| 实测数据 | **2,343 行** |

**覆盖范围**：局内战斗核心循环 · 单局战术决策状态机 · Boss 战循环 · 局外花园种植系统 · 皮肤商业化 · 资源流转闭环 · 关键数值锚点

**拆解结论示例**

- 花园系统用「位置稀缺」（11 种可种植物 vs 8 个花圃位）做取舍，而不是加产出上限
- 宝石作为唯一通货，同时承担硬通货与养成入口，把两个本会打架的循环焊成一个
- 伤害曲线采用「顺位配平」而非「数值配平」——玩家感知整齐，代价是插入新武器时难以不破坏顺位

**输出**：7 条改进提案，按优先级排序，每条配执行方案、验收标准、成本评估与风险

## 03 · 《山海契》动作 RPG · 契约养成

**性质**：完整原创方案 + 可验证数值层 ｜ PC 单机 · 第三人称低模 3D · 无联网、无内购

> 你在山海之间行走，收下妖留下的蛋，或与幼崽立契；妖能替你打，也能反咬你——**契约不是收服，是长期共处**。

| 指标 | 数量 |
| --- | --- |
| 主方案 | **849 行**（约 1.7 万字） |
| 内容规模 | 3 区域 / 30 探索节点 / **14 种妖** / **18 件近战兵器** / 4 类射器 / 16 种消耗品 |
| 数值表 | **16 张工作表 / 374 数据行** |
| 数值层代码 | 7 个 C# 模块 + 3 份 JSON（兵器 18 / 妖 14 / 消耗品 16） |
| 自动验证 | **178 条断言，`dotnet run` 输出 PASS** |

**三个核心设计**

1. **契约不是收服，是共处** —— 强行签约永远可选，但代价是一次押上性命的赌：主角与妖的战力比直接换算成反噬概率（R=2.51 时 45%，跌破 1.25 直接跳到 100%），契约期内每天都要重新兑现。
2. **妖不会因为你打赢它就服从** —— 信赖值只能靠喂食、疗伤、并肩、让它自己做决定来养，且每天自动衰减（100 − 90×0.8 = 28.0）。
3. **18 件兵器不做上位替代** —— 共用一条预算线，任意两件在「输出 / 触及 / 横扫角 / 耐久」四轴上严格支配关系为 **0 对**（C(17,2)=136 组全查）。

**工程化验证（这份作品的差异点）**

数值层写成**零 UnityEngine 依赖**的独立程序集（`noEngineReferences = true`）——不是靠注释约定，是编译器强制。配套命令行验证程序覆盖 178 条断言：原文算例、边界夹取、跳档落差、支配关系。

破坏性自检：把「锏」的耐久从 265 改成 150 → 程序立刻报出 2 对支配并 FAIL；改回即恢复 0 对。这说明判定是真的在测数据，不是「随便变个数就报警」。

## 04 · 《烽线》写实向 PVE 战役射击

**性质**：原创方案 + 枪械参数体系 ｜ 只出方案、不做原型（理由写在方案 §1.3 的人力估算里）

> 从黑火药到自动火器，一支民间抵抗武装用几十年时间追上一个工业帝国——**枪越打越好，人越打越少**。

| 指标 | 数量 |
| --- | --- |
| 主方案 | **852 行**（约 1.9 万字） |
| 枪械参数体系 | **608 行 / 27 把枪 / 295 行参数表** |
| 数值表 | **2 册 / 22 张工作表 / 480 数据行** |

**两个设计主张**

1. **武器代差本身就是进度条** —— 时间轴从黑火药走到自动火器，玩家手里那把枪永远比对面差半代，只能用地形、耐心和缴获把半代补回来。
2. **弹药口径就是货币** —— 单关射击弹药按「发」计，不做无脑连射；经济压力直接来自补给。

**参数模型**：每把枪给出口径 / 初速 / 射速 / 单发伤害 / 有效射程 / 精度 MOA / 垂直与水平后坐 / 50–300 m 下坠 / 开镜与换弹时间 / 重量 / 配件槽；TTK 用统一公式计算，同档位**严格支配关系为 0**。

**数据纪律**：每条数据标 **A / B / C** 三级可信度，C 级必须写明估算依据；不编造番号与年份，世界观内一切专名均为虚构自造。
